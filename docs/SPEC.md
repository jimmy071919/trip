# 地圖式行程規劃與交通紀錄系統 — 軟體需求規格書（SRS）

- 版本：v1.0（MVP 規格）
- 日期：2026-11-01
- 狀態：可交付開發的初版規格；未另行確認的項目採用「個人自架、單一管理者、桌面優先、支援手機瀏覽」作為預設。
- 專案代號：Map Trip Planner

> 文末「附錄：實作對照」說明 v1.0 實作在規格未明訂處所做的決定。

## 1. 專案目標

開發一套可透過 Docker Compose 自行部署的 Web 應用程式，讓使用者直接在互動式地圖上新增／拖曳點位、儲存地點相關資訊、安排地點順序，並針對「兩個地點之間的路段」記錄交通方式、費用、時間及自由文字說明。關閉或重啟容器後資料仍須保留。

### 1.1 核心原則

1. 地圖操作優先：不用先知道經緯度；點選地圖即可建立點位，拖曳既有標記可調整位置。
2. 地點與交通分離：地點（Stop）儲存「在哪裡、做什麼」；路段（Leg）儲存「如何從 A 到 B」。
3. 使用者可完全手動編輯：不強制使用自動導航、地址搜尋或第三方交通 API。
4. 自架、可攜、可備份：Docker Compose 啟停、資料持久化、JSON 備份與還原。
5. 先完成實用 MVP：第一版採「依順序連接點位的直線」示意交通關係，不將其誤稱為實際道路導航路線。

### 1.2 使用情境

使用者建立「2026 日本旅行」專案，選擇 11 月 5 日，在地圖上新增「飯店 → 車站 → 景點」。每個點位可補充營業時間、行程內容或備註；飯店到車站設為「步行／15 分鐘」，車站到景點設為「電車／40 分鐘／¥580」，並儲存車次、乘車說明或外部連結。重新開啟瀏覽器後仍能編輯。

## 2. 角色與範圍

- 主要角色：管理者（單一帳號）；可登入並操作所有專案。
- 裝置：桌面瀏覽器優先，手機版需可用。
- 運行環境：Linux 主機，安裝 Docker Engine 與 Docker Compose Plugin。
- MVP 不包含：多人即時協作、AI 自動規劃、全自動大眾運輸時刻表、道路級語音導航、離線地圖下載。

## 3. 核心資料定義

| 名詞 | 定義 | 例子 |
| --- | --- | --- |
| 專案 Project | 一張可管理點位與路線的地圖，可命名並附描述 | 東京五日遊、台灣咖啡地圖 |
| 日期 Day | 專案中的可選行程分組；也允許「未排程點位」 | 2026-11-05 |
| 地點 Stop | 地圖上的一個標記，包含經緯度及地點資訊 | 東京車站 |
| 路段 Leg | 同一日期內，兩個相鄰已排序地點之間的交通紀錄 | 東京車站 → 淺草 |
| 路段線 Polyline | 畫在地圖上的視覺連線，MVP 為直線 | 兩標記間的虛線 |

> 注意：交通方式屬於路段而非地點。同一個景點可以搭不同交通工具抵達，因此不能把交通工具只存成景點的固定屬性。

## 4. 功能需求

優先級定義：P0 = MVP 必須完成；P1 = 第二階段；P2 = 未來擴充。

### 4.1 專案管理

| 編號 | 優先級 | 需求 |
| --- | --- | --- |
| PRJ-01 | P0 | 建立、重新命名、修改描述、刪除專案；刪除需二次確認。 |
| PRJ-02 | P0 | 列出所有專案，點擊後載入專案地圖及資料。 |
| PRJ-03 | P0 | 設定專案預設地圖中心及縮放；下次開啟還原檢視。 |
| PRJ-04 | P0 | 可建立多個日期分組；可新增不屬於日期的「未排程點位」。 |
| PRJ-05 | P1 | 複製專案、套用既有行程模板。 |

### 4.2 地圖及點位操作

| 編號 | 優先級 | 需求 |
| --- | --- | --- |
| MAP-01 | P0 | 地圖支援平移、放大、縮小，並有來源標示。 |
| MAP-02 | P0 | 按「新增地點」後點擊地圖任意位置，建立一個可編輯的標記。 |
| MAP-03 | P0 | 地圖標記可拖曳；拖曳結束即更新經緯度，並儲存至後端。 |
| MAP-04 | P0 | 點擊標記，右側顯示對應資訊面板；目前選取的標記須突出顯示。 |
| MAP-05 | P0 | 可編輯、刪除地點；刪除前確認，並處理相關路段。 |
| MAP-06 | P0 | 可依日期顯示／隱藏點位；未排程點位另設圖層。 |
| MAP-07 | P0 | 地點排序後，地圖依序繪製連線；標記顯示順序號碼。 |
| MAP-08 | P0 | 可直接輸入緯度、經度修正位置，並驗證合法範圍。 |
| MAP-09 | P1 | 地點名稱／地址搜尋，選取搜尋結果後加入地圖。 |
| MAP-10 | P1 | 自訂標記圖示、顏色、標籤與分類篩選。 |
| MAP-11 | P1 | 使用者可在 A→B 路段中新增／拖曳中途控制點，手動繪製更貼近實際的線。 |

互動細則：

- 新增點位時，畫面先顯示暫存標記及編輯表單；使用者儲存後成為正式地點，取消則移除暫存標記。
- 拖曳標記時，地圖中的連線即時跟隨；在 dragend 後呼叫儲存 API。
- 新增點位若尚未選擇日期，預設歸類為「未排程點位」。
- 地圖不允許因一般平移／點擊而誤新增多個標記；必須先進入新增模式。

| 編號 | 優先級 | 需求 |
| --- | --- | --- |
| STOP-01 | P0 | 地點名稱（必填）、緯度／經度（必填）、自由文字內容／備註（選填）。 |
| STOP-02 | P0 | 可儲存地址文字、外部網址、預計抵達時間、預計停留分鐘數（均選填）。 |
| STOP-03 | P0 | 同一日期內，左側清單可拖曳重新排序點位。 |
| STOP-04 | P0 | 可將點位移到另一日期或改為未排程；更新相鄰路段關係。 |
| STOP-05 | P1 | 點位可上傳照片、附件及自訂標籤。 |
| STOP-06 | P1 | 地點詳細內容支援安全的 Markdown 格式編輯／顯示。 |

### 4.4 路段與交通紀錄

| 編號 | 優先級 | 需求 |
| --- | --- | --- |
| LEG-01 | P0 | 同一天內，相鄰已排序地點之間自動形成路段，例如 A→B、B→C。 |
| LEG-02 | P0 | 點擊地圖上的路段線，或點擊清單中的交通資訊，即可編輯路段。 |
| LEG-03 | P0 | 交通方式可選：步行、腳踏車、機車、汽車、公車、捷運／地鐵、火車／高鐵、計程車、渡輪、飛機、其他。 |
| LEG-04 | P0 | 每個路段可儲存：交通方式、路線／班次、預估時間、費用、幣別、補充內容、參考網址。 |
| LEG-05 | P0 | 路段資料為人工紀錄；費用、時間不可假裝成系統已精確估算。 |
| LEG-06 | P0 | 改變點位順序時，路段依 from_stop_id + to_stop_id 配對；若來源／目的地配對改變，原有資訊不得錯誤套到新路段。 |
| LEG-07 | P0 | 對新形成而未填寫的路段顯示「未設定交通方式」。 |
| LEG-08 | P1 | 可接第三方路由服務，取得部分交通模式的實際道路形狀、距離與預估時間。 |
| LEG-09 | P2 | 可整合地區性大眾運輸資料，提供實際班次／轉乘規劃。 |

重排規則：若原順序 A→B→C 改成 A→C→B，A→B 的資料不應被誤用為 A→C。系統應依起訖點識別路段，保存可沿用的同一對起訖點資料，其餘路段重新建立或標記待確認。

交通線條規則：MVP 只展示「兩地有交通關係」的直線，不聲稱沿道路或軌道計算。即使選擇捷運、火車或飛機也能記錄文字，但不在第一版自動繪製實際線路。

## 6. 建議技術架構

| 層級 | 技術 | 用途 |
| --- | --- | --- |
| 前端 | React + TypeScript + Vite | 單頁應用程式、表單與互動狀態 |
| 地圖 | Leaflet + React Leaflet | 地圖、標記、拖曳、連線 |
| UI | Tailwind CSS | 響應式版面 |
| 後端 | Python FastAPI | REST API、資料驗證、登入／匯入匯出 |
| ORM／Migration | SQLAlchemy + Alembic | 資料庫物件及版本升級 |
| 資料庫 | PostgreSQL | 儲存專案、點位、路段與使用者 |
| Web Server | Nginx | 提供前端靜態檔案及反向代理 /api |
| 部署 | Docker Compose | 管理 web、api、db 服務 |
| 地圖底圖 | 可設定供應商的 OSM 衍生底圖 | 展示互動地圖；需遵守供應商授權與用量政策 |

技術決策：MVP 不必引入 PostGIS；單純儲存 latitude / longitude（雙精度數值）已足夠。未來如加入空間查詢、附近搜尋，再評估 PostGIS。

底圖策略：地圖套件與底圖服務應解耦，底圖 URL 與 attribution 不應寫死。OpenStreetMap 的資料雖可自由使用，官方公開圖磚服務有流量、快取與禁止大量下載等要求；公開或高流量部署時應改用合規的商業／自架圖磚服務。地點地址搜尋並非 MVP 必要功能；後續若用 Nominatim 公共 API，必須遵守限流與禁止自動完成查詢等政策。

## 7. 資料庫模型

所有識別碼建議使用 UUID，所有時間戳以 UTC 儲存，前端依使用者指定時區顯示。

- **users**：id UUID PK；username TEXT UNIQUE NOT NULL；password_hash TEXT NOT NULL；created_at, updated_at TIMESTAMPTZ
- **projects**：id UUID PK；owner_id UUID FK → users.id；title TEXT NOT NULL；description TEXT NULL；timezone TEXT NOT NULL DEFAULT 'Asia/Taipei'；map_center_lat / map_center_lon DOUBLE PRECISION；map_zoom INTEGER；created_at, updated_at
- **days**：id UUID PK；project_id UUID FK → projects.id；date DATE NULL；title TEXT NULL；sort_order INTEGER NOT NULL；created_at, updated_at
- **stops**：id UUID PK；project_id FK；day_id UUID NULL FK → days.id（NULL = 未排程）；title TEXT NOT NULL；latitude DOUBLE PRECISION NOT NULL（-90～90）；longitude DOUBLE PRECISION NOT NULL（-180～180）；address、description、reference_url TEXT NULL；arrival_time TIME NULL；stay_minutes INTEGER NULL（>= 0）；sort_order INTEGER NULL；created_at, updated_at
- **legs**：id UUID PK；project_id FK；day_id FK；from_stop_id FK → stops.id；to_stop_id FK → stops.id；transport_mode TEXT NULL；route_name TEXT NULL；duration_minutes INTEGER NULL（>= 0）；cost_amount NUMERIC(12,2) NULL（>= 0）；currency CHAR(3) NULL（ISO 4217）；description、reference_url TEXT NULL；created_at, updated_at

關聯約束：路段起訖地點不可相同，必須屬於同一專案且同一行程日；後端應用交易處理排序、刪除、轉移及路段重建。需避免同一日出現重複的同向有效路段。

資料刪除：刪除專案連帶刪除其日程、地點及路段；刪除地點會刪除或重新整理所關聯的路段；操作前需明確提醒。

## 8. REST API（建議契約）

所有 API 使用 `/api/v1` 前綴，以 JSON 收發，HTTP 回應碼及錯誤結構應一致；所有資源都檢查登入者對專案的存取權。

| 方法 | 路徑 | 說明 |
| --- | --- | --- |
| POST | /auth/login | 登入 |
| POST | /auth/logout | 登出 |
| GET | /auth/me | 目前登入者 |
| GET / POST | /projects | 列表／建立專案 |
| GET / PATCH / DELETE | /projects/{project_id} | 讀取／修改／刪除專案 |
| GET / POST | /projects/{project_id}/days | 日期列表／新增日期 |
| PATCH / DELETE | /days/{day_id} | 修改／刪除日期 |
| GET / POST | /projects/{project_id}/stops | 地點列表／新增地點 |
| PATCH / DELETE | /stops/{stop_id} | 更新（含拖曳座標）／刪除地點 |
| PUT | /days/{day_id}/stop-order | 以 stop ID 陣列原子性更新排序與路段 |
| GET / POST | /days/{day_id}/legs | 路段列表／建立路段（視排序自動管理） |
| PATCH | /legs/{leg_id} | 更新交通資訊 |
| GET | /projects/{project_id}/export | 下載完整 JSON 備份 |
| POST | /projects/import | 匯入 JSON 建立新專案 |
| GET | /health | 服務健康檢查 |

API 必須檢查所有數值範圍、時間格式、網址類型、路段關係及專案所有權；更新失敗回傳可閱讀的欄位錯誤，不可只回 500。

## 9. Docker Compose 與交付要求

- `web`、`api`、`db` 三個服務均由 compose.yaml 管理。
- `web` 暴露可設定的主機連接埠（預設 8080）；`api` 與 `db` 不直接對外開放連接埠。
- `db` 使用 named volume 保存資料，容器重建、`docker compose down` / `up` 不得導致資料消失。
- 資料庫設置 healthcheck；API 啟動需考慮資料庫就緒狀態，並提供 Migration 流程。
- 服務加入合理的 restart policy、日誌與基本健康檢查。
- 可由 .env 設定主機埠號、DB 帳密、登入初始設定、時區、底圖網址與授權文字。
- 不得把正式帳密直接寫在 compose.yaml 或版本庫；提供 .env.example 但不得上傳真實 .env。
- 對外公開時需使用 HTTPS 反向代理、Secure Cookie 與適當的主機防火牆設定。
- 完整備份需同時涵蓋資料庫及未來新增的附件檔案；僅匯出專案 JSON 不等於系統全量備份。

> 警告：`docker compose down -v` 會移除 Compose 管理的 named volumes，若資料庫未另行備份，可能造成資料遺失；不得把它寫成一般關閉指令。

## 10. 非功能需求

| 面向 | MVP 要求 |
| --- | --- |
| 瀏覽器 | 最新穩定版 Chrome、Firefox、Edge；手機瀏覽器基本操作可用 |
| 語系 | 初版繁體中文介面；欄位及程式命名用英文 |
| 資料持久化 | 容器停止、重建、主機重啟後資料仍在（前提：volume 保留） |
| 資料正確性 | 修改位置、排序、刪除須使用後端驗證及交易，避免留下孤立路段 |
| 反應 | 一般地圖互動不因編輯表單卡頓；目標支援單專案至少 200 個點位 |
| 儲存狀態 | 每次寫入操作都要告知結果；網路斷線時顯示可辨識錯誤並提供重試 |
| 安全性 | 雜湊密碼、授權檢查、輸入驗證、合理的 Cookie 安全屬性、CSRF 防護策略 |
| 可維護性 | 具自動化 API 測試及基本前端流程測試；附 README 和資料庫 migration |
| 隱私 | 對第三方地圖服務傳送資訊時遵守其政策；不把私人筆記內容送去地圖 API |
| 備份 | 專案層級 JSON 匯出／還原可用，且需提供完整資料庫備份說明 |

## 11. 使用者故事與驗收條件

- **AC-01 建立點位**：登入並開啟專案 → 「新增地點」→ 點地圖、輸入名稱、儲存 → 地圖顯示該點位，左側列表可見，重新整理後仍存在。
- **AC-02 拖曳點位**：拖曳 A 到新位置 → 標記與相連線段即時更新；儲存完成後重新整理，新經緯度不變。
- **AC-03 記錄交通資訊**：日期 D 有 A、B、C → 設定 A→B 為火車、費用、時間、描述 → 詳情面板及清單顯示；重新整理後一致，B→C 不受影響。
- **AC-04 重排不串資料**：A→B 步行、B→C 火車 → 重排為 A→C→B → 「步行」不可掛到 A→C，「火車」不可掛到 C→B。
- **AC-05 刪除保護**：A→B→C 刪除 B → B 與涉及 B 的路段清除或依規則重建；不可留下指向不存在點位的有效路段。
- **AC-06 持久化**：`docker compose down` 再 `docker compose up -d` → 所有專案、點位及路段仍在。
- **AC-07 備份還原**：匯出 JSON，匯入至新建空白系統 → 日期、座標、排序、路段和各欄位完整還原且關聯正確。
- **AC-08 部署**：全新 Linux 主機依 README 設定 .env 並 `docker compose up -d --build` → 可在 `http://<主機IP>:8080` 完成初始管理者設定與登入，且 db 不直接開放到外部網路。
- **AC-09 錯誤回饋**：API 暫時無法連線時更新點位 → 前端顯示「儲存失敗」與重試，不能出現「已儲存」的誤導狀態。

## 12. 測試與開發交付

必須測試：後端單元／整合測試（專案 CRUD、點位 CRUD、座標範圍、日期關係、路段重排、權限、JSON 匯入匯出）；前端互動測試（新增點位、選取標記、拖曳後保存、變更排序、交通編輯、顯示儲存失敗）；E2E 測試（登入到新增行程、編輯、重啟服務、重新登入確認資料）；部署測試（新環境依 README 啟動，健康檢查通過，無 API／資料庫對外暴露）。

Definition of Done：P0 需求與驗收條件全部通過；`docker compose up -d --build` 可由乾淨專案建置與啟動；README 提供首次建置、更新、停止、資料備份、還原、疑難排除；API 文件可透過 FastAPI OpenAPI 生成；至少一份可匯入的示範資料；專案可在沒有地點搜尋或自動路由服務時正常使用。

## 13. 開發里程碑

1. Phase A — 基礎部署：Compose、API、資料庫、登入與 Migration。
2. Phase B — 地圖編輯：建立專案、地圖點選新增、拖曳點位、詳情面板、資料持久化。
3. Phase C — 行程與交通：日期分類、點位排序、路段連線、交通資料、重排規則。
4. Phase D — 品質與備份：JSON 匯出匯入、權限與測試、手機版、部署文件。
5. Phase E — 後續擴充：搜尋、手動畫折線、自動道路路由、附件、GeoJSON、多人協作。
